Executive summary

The DsQt TouchEngine integration was rewritten from a collection of manager-based QML wrappers, custom texture nodes, and backend-specific renderers into a reusable Qt Quick module built around Qt's Rendering Hardware Interface (QRhi).

The former API centered on DsTouchEngineManager, instance identifiers, DsTouchEngineInstance, and separate types for individual input and output categories. Applications had to coordinate manager initialization, instance creation and recreation, component loading, and view attachment.

The rewrite replaces that model with three principal public types:

  • DsTouchEngineSession owns the logical component and its state.
  • DsTouchEngineView displays one texture output from a session.
  • DsTouchEngineTypes supplies state, graphics, link, and timing enums.

Internally, the module reuses Qt's graphics device, command queue, and context; isolates graphics work on the render thread; performs explicit native resource ownership transfers; and preserves desired session state across reloads and renderer recreation.

The principal rewrite changed roughly 128 files, adding about 13,000 lines and removing about 8,500. Later work integrated the module into ClonerSource and NewTouchDemo, made Vulkan dependencies conditional for consumers, added runtime diagnostics, and corrected performance and texture-identity problems in D3D12, OpenGL, and Vulkan.

Why the rewrite was needed

Application-managed engine instances

The legacy ClonerSource QML had to:

  1. Ask DsTouchEngineManager to create an instance.
  2. Store the returned identifier.
  3. Retrieve a DsTouchEngineInstance.
  4. Wait for manager initialization.
  5. Respond when the manager recreated the instance.
  6. Assign the component path and invoke the old loading method.
  7. Pass the instance identifier to every output view.

This exposed internal lifecycle mechanics to every application screen using TouchEngine.

Fragmented value API

Numeric, string, table, float-buffer, and texture values used separate public QObject types, split again by input and output direction. This made simple use cases verbose and made consistent lifecycle and error handling difficult.

Graphics code outside Qt Quick's lifecycle

The legacy implementation maintained custom renderer, image, texture, material, and scene-graph classes for individual graphics APIs. It was difficult to prove that TouchEngine resource operations used the same native device, queue, and lifetime boundaries as Qt Quick.

Unclear destruction and recreation behavior

A logical TouchEngine component may outlive a Qt renderer, while a view may outlive its session. The old manager-and-ID design made these transitions hard for applications to reason about and test.

Architecture goals

  • Represent each loaded component with one logical session.
  • Allow any number of views to share that session.
  • Remove application-visible engine instance identifiers.
  • Select the TouchEngine backend from Qt's active QRhi API.
  • Perform native graphics operations only on the Qt Quick render thread.
  • Keep Qt-owned output textures stable across TouchEngine pool reuse.
  • Make load, unload, reload, and renderer recreation deterministic.
  • Expose a common API to QML and C++.
  • Support scalar, string, table, float-buffer, and QML texture values.
  • Provide fast tests plus optional real-GPU tests for all four backends.

Architecture after the rewrite

LayerResponsibility

Shared stateThread-safe commands, events, durable desired state, and renderer coordination.

Texture output flow:

TouchEngine native texture → backend import → QRhi copy → stable link-owned Qt texture → DsTouchEngineView

QML texture input flow:

QML texture provider → QRhi staging texture → backend exportable texture → TouchEngine input

TouchEngine's native texture and the texture displayed by Qt do not have the same ownership or lifetime. Keeping them separate is the central protection against output swapping and premature native-resource destruction.

DsTouchEngineView

DsTouchEngineView derives from QQuickRhiItem. Its session property selects the session, outputLink selects the texture output, and clearColor supplies the background when no output is available.

The session is stored through QPointer. Destroying a live session clears the view reference instead of leaving a dangling pointer.

DsTouchEngineTypes

This type is exposed to QML as the uncreatable DsTouchEngine enum container. It supplies session states, graphics APIs, time modes, link scopes, and link data types.

QML migration

Previous ClonerSource design

The old TouchDesigner.qml created an instance through the manager, stored its ID, retrieved an engine object, listened for manager initialization and recreation, loaded the component, and declared four nearly identical output views.

Rewritten design

The rewritten component creates one DsTouchEngineSession with a component path, a requested 60 FPS frame rate, and automatic running enabled. It calls load() on completion.

A Repeater creates four DsTouchEngineView objects for op/out1 through op/out4. Every view shares the same session but selects a different output link. The screen displays errorString when loading, rendering, or backend operations fail.

Compatibility type

DsTouchEngineTextureView.qml remains as an alias for DsTouchEngineView. It preserves the old type name for limited source compatibility, but it does not restore the former instanceId or autoUpdate contract.

Threading, ownership, and lifecycle

Application thread

DsTouchEngineSession owns the public QObject and QML state. Its setters update durable desired state and enqueue commands instead of issuing native graphics operations directly.

Qt Quick render thread

DsTouchEngineView creates a QQuickRhiItemRenderer. The renderer receives Qt's current QRhi and command buffer, stages QML texture inputs, asks the core to process work, draws the selected stable output, and finalizes native transfers after the frame ends.

TouchEngine callbacks

TouchEngine callbacks enqueue lightweight records under a mutex. They do not mutate QML objects or issue graphics commands. A callback-drain flag wakes the views so state and statistics records are not left pending when no other visual change requests a frame.

Load and renderer attachment

A load requested before a renderer exists enters WaitingForRenderer. When a view supplies an active QRhi, the core creates the matching backend, creates the TouchEngine instance, associates its graphics context, and loads the component.

Unload and reload

Unload stops new work, observes the TouchEngine lifecycle callbacks, releases the component and instance, clears runtime link state, and resets backend state belonging to that instance. Releasing the TEInstance is the callback lifetime fence.

Reload performs a controlled unload followed by a fresh instance load. Durable configuration and input state are replayed. Backend caches tied to the old native texture pool are cleared at this boundary.

Renderer recreation

Qt may recreate its scene graph while the public session remains alive. Desired application state stays in shared storage; the old render-side resources are released, and the replacement renderer creates a new backend and replays that state.

Graphics backends

TouchEngineRhiBackend defines one contract for D3D11, D3D12, Vulkan, and OpenGL. It initializes against Qt's QRhi, supplies a TouchEngine graphics context, negotiates capabilities, stages inputs, imports and copies outputs, maintains stable per-link caches, and finalizes transfers after the Qt frame ends.

D3D11

D3D11 proved to be the most stable initial implementation and became the control backend. It demonstrated that the test component, session scheduler, and QML presentation could operate without progressive slowdown.

D3D12

The first D3D12 path repeatedly opened native shared texture and fence handles. This caused native object and wrapper churn. Texture imports now cache the TouchEngine texture identity, NT handle, ID3D12Resource, QRhi wrapper, dimensions, format, and last-use serial. Fence imports similarly cache the TouchEngine semaphore, handle, and ID3D12Fence.

Texture and fence caches are bounded to 32 and 16 entries. Pending and retired transfers retain shared ownership so in-flight resources cannot be pruned. When a new TouchEngine instance is configured, reusable caches are cleared while retired GPU work keeps only the objects it still needs.

OpenGL

On Windows, TouchEngine can supply a D3D shared texture while Qt uses OpenGL. The backend converts that source through TEOpenGLContextGetTexture, locks it, copies it, and later unlocks it.

The original path flushed and unlocked every output independently. The final path records all pending unlocks, performs one flush after the frame, unlocks the batch, and publishes the stable output caches. A cross-frame conversion cache was tested and removed after a later reload hung.

Vulkan

Vulkan reuses Qt's VkInstance, physical device, logical device, graphics queue, queue family, and command buffer. The backend enables the external-memory and external-semaphore extensions required by TouchEngine.

The four-output test exposed link swapping because an imported native resource could become associated with whichever output link most recently supplied it. Imported resources are now keyed by native TouchEngine and Vulkan identity, while every output link retains a stable Qt-side texture. Ambiguous reuse of one native source through multiple links in the same frame is deferred, preserving the affected link's previous stable frame.

Binary TouchEngine waits and signals are composed into Qt's existing Vulkan queue submission, and ownership and layout barriers are recorded in Qt's command buffer. Timeline-semaphore cases retain a native-submit fallback. Host-return binary semaphores are cached per imported texture and reused only after the same texture has returned from TouchEngine, proving the previous signal was consumed.

The dsqt.touchengine.vulkan.mapping logging category records link, TouchEngine object, external handle, VkImage, Qt cache, and frame slot to support future identity investigations.

Frame scheduling and runtime diagnostics

Scheduler correction

The initial scheduler restarted a full interval from the current time whenever a frame was late. Repeated small delays could therefore reduce the achieved TouchEngine rate. The revised scheduler keeps the original phase and advances by whole elapsed intervals until the next target is in the future.

TouchEngine still depends on Qt render-thread opportunities for GPU work and callback draining, but ordinary lateness no longer adds an unnecessary extra interval. requestFrame() remains available for manual operation.

TouchEngine statistics

Qt presentation FPS can remain high while TouchEngine completes frames more slowly. The module registers TEInstanceSetStatisticsCallback and exposes CPU and GPU frame time, measured frames, dropped frames, and CPU and GPU memory. Statistics reset when the session leaves Ready.

Runtime versions

On Windows, the session locates the loaded TouchEngine.dll module and reads its product-version metadata. This reports the DLL actually loaded by the process.

After TouchEngine configuration, the core calls TEInstanceGetConfiguredEnginePath. The session reads the product version from TouchDesigner.exe, with bin/TouchEngine.exe as a fallback.

NewTouchDemo and graphics testing

NewTouchDemo was migrated to the session-and-view API and became the primary interactive graphics test application. It currently loads four_out10.tox and displays op/out1 through op/out4.

F3 diagnostics

Pressing F3 toggles an overlay containing:

  • Qt presentation FPS
  • TouchEngine completed-frame FPS
  • TouchEngine CPU and GPU frame time
  • Dropped and measured frame counts
  • CPU and GPU memory usage
  • Loaded TouchEngine SDK DLL version
  • Configured TouchDesigner engine version

Graphics API and color depth

DSQT_GRAPHICS_API, with QSG_RHI_BACKEND as a fallback, selects d3d11, d3d12, vulkan, or opengl. D3D12 is the default. DSQT_COLOR_DEPTH accepts 8 or 10, with 10 as the current default.

The application logs the requested and active API, requested and effective bit depth, and actual surface channel sizes. OpenGL treats a requested 10-bit mode as effectively 8-bit in the current test configuration.

Ten-bit output and HDR

Ten-bit transport and HDR color correctness are separate. Correct HDR10 output also requires the source, renderer, swapchain, and display to agree on transfer function, primaries, and tone mapping. The observed oversaturation is therefore not the same problem as backend synchronization or texture identity.

Build and packaging rewrite

SDK layout and version gate

The SDK now resides under Library/DsQt/TouchEngine/sdk:

  • include contains TouchEngine headers.
  • lib contains the import library.
  • bin contains the runtime DLL.
  • The license and SDK change history are packaged with the module.

Configuration checks for TEInstanceLinkGetChoices, introduced with TouchEngine 3.3, and fails early when the SDK payload is incomplete or stale.

Static QML module and shaders

The module is built with qt_add_qml_module under the URI Dsqt.TouchEngine. Checked-in compiled shader files and standalone shader scripts were removed. qt_add_shaders now produces the QRhi variants using the Qt version performing the build.

Installed target graph

A static Qt QML module includes resource objects, plugin initialization, shader resources, and generated object libraries in addition to its primary archive. The install exports that complete target graph through DsqtTouchEngineTargets.cmake.

Configuration-specific runtime

TouchEngine runtime and import libraries install into Debug, Release, and RelWithDebInfo directories. MinSizeRel maps to Release, and consuming applications copy the matching DLL beside their executable.

Conditional TouchEngine and Vulkan dependencies

An application requesting only Dsqt::Core should not need to find Vulkan or inspect TouchEngine targets. The installed package now creates those targets only when TouchEngine is requested. TouchEngine itself requires Vulkan because its static module contains the Vulkan backend.

ClonerSource provides DS_APP_ENABLE_TOUCHENGINE and DS_APP_ENABLE_SPOUT, both defaulting to OFF. When TouchEngine is disabled, its QML file, plugin import, libraries, runtime copy, and vcpkg feature are all omitted.

vcpkg featureAdditional dependency
touchengineVulkan
spoutVulkan

CMake selects manifest features before project(), when vcpkg first resolves the manifest. A no-components package lookup still represents the all-modules umbrella and therefore requires every included module dependency.

ProjectCloner and Qt Creator configuration

Qt Creator reported that no CMake configuration matched the available Debug, Release, and RelWithDebInfo configurations. The generated preset mixed single-config assumptions with Qt Creator's selected build type.

ProjectCloner now generates a Ninja Multi-Config configure preset with those three configurations and separate build presets for each one. It also detects Qt installations, Visual Studio 2019/2022/2026 through vswhere, and Ninja from PATH, Qt, or Visual Studio.

build_and_install.bat was updated to:

  • Preserve an explicitly configured standalone VCPKG_ROOT.
  • Bootstrap the vcpkg executable when scripts require a newer version.
  • Detect a build cache created with a different vcpkg toolchain.
  • Resolve and log the Ninja executable.
  • Clear stale vcpkg PowerShell cache paths.
  • Support -force-install after an otherwise no-op build.

Testing strategy

Fast tests

C++ tests cover session defaults, property changes, commands, link metadata, input validation, event purging, lifecycle behavior, statistics, and versions. QML tests verify type registration, enums, writable properties, read-only defaults, invokable methods, statistics, and version properties.

Installed-package test

A small consumer verifies that the installed static QML module can be found, linked, imported, and executed with its generated plugin and resource targets.

Real texture-input test

The input test creates a QML texture source, publishes it to TouchEngine, receives the processed output, and captures the result under D3D11, D3D12, Vulkan, and OpenGL.

Multi-output lifecycle test

The expanded real-GPU test:

  • Finds every texture output.
  • Creates one view per output and arranges the views in a grid.
  • Measures 30 completed TouchEngine frames per epoch.
  • Runs an initial load plus three reload cycles.
  • Changes the window size between epochs.
  • Captures three images per epoch.
  • Records backend, API, outputs, frames, elapsed time, and FPS.
  • Destroys the live session and confirms that every view detaches safely.

Texture-identity regression check

Each captured tile is sampled into a mean RGB signature. Later captures are compared with the first capture in the same epoch. The test reports a failure only when visually distinct outputs confidently cross to different links. If the outputs are too similar, it skips the identity conclusion instead of producing an unreliable result.

Performance investigation process

  1. Measure Qt and TouchEngine separately. The F3 overlay showed that Qt could remain at 60 or 90 FPS while TouchEngine declined.
  2. Check display and VSync behavior. Changing presentation timing did not prevent TouchEngine degradation.
  3. Use Release builds. Release reproduced the problem, ruling out Debug overhead as the primary cause.
  4. Compare APIs. D3D11 remained stable enough to serve as the control.
  5. Stress four outputs. four_out10.tox amplified per-output synchronization and native-pool behavior.
  6. Add reload cycles. This exposed caches that retained objects across instance boundaries.
  7. Capture output identity. Performance measurements alone could not detect Vulkan link swapping.
  8. Retain only lifecycle-safe optimizations. The unsafe OpenGL cache was removed; D3D12 caches were scoped to one instance; Vulkan semaphore reuse was retained only after its lifecycle could be proven.

Remaining work

OpenGL performance

OpenGL is stable but remains slower than the native D3D and Vulkan paths on Windows. Further improvement requires a lifecycle-safe reduction in the D3D-to-OpenGL conversion cost.

HDR color management

The application can request a 10-bit surface, but correct HDR10 output still requires an explicit policy for swapchain color space, transfer function, primaries, texture encoding, SDR conversion, tone mapping, and display state.

Longer endurance tests

A longer mode could record moving-average FPS, worst frame time, cache sizes, pending and retired transfer counts, GPU-memory growth, callback continuity, and texture-identity failures over dozens of reloads.

Additional link types

New TouchDesigner data categories should extend the common session API rather than reintroducing one public QObject class per data type.

Conclusion

This work began as a full architectural rewrite, not a narrow Vulkan or frame-rate patch. The manager, instance-ID, custom renderer, and per-type wrapper system was replaced by a session-and-view API built around QRhi and QQuickRhiItem.

That foundation made the later backend corrections possible: D3D12 imports are reused without retaining obsolete instance pools; OpenGL output synchronization is batched without an unsafe conversion cache; Vulkan synchronization is composed with Qt's submission; Vulkan return semaphores are safely reused; and stable link-owned display textures prevent TouchEngine pool reuse from swapping outputs.

The result is both a replacement public API and a more rigorous graphics, lifecycle, packaging, diagnostics, and testing foundation for future TouchDesigner work in DsQt.
